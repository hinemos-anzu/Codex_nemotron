## What “Golden prediction log” means

For Phase3, a **Golden prediction log** means a row-level validation inference artifact generated with the exact Golden Baseline inference settings. It should contain at least:

- `problem_id`
- `question`
- `gold_answer`
- `pred_answer`
- `raw_output`
- `reasoning_text`
- `final_answer_text`
- `is_correct`
- `parse_success`
- `parse_error_type`
- `generation_token_count`
- `finish_reason`

If token scores are available, the companion logprob artifact should also contain `min_logprob`, `mean_logprob`, `answer_min_logprob`, and `answer_mean_logprob`.

Therefore, the notebook's existing diagnostic logs are **not sufficient** as Golden prediction logs. They are useful only for adapter packaging/compression validation.

## Do we need to add logging to the Golden Baseline?

No, not for the first Phase3 pass if the priority is to avoid touching the Golden Baseline notebook. Adding a logging observer would produce the best measured accuracy/failure/logprob analysis, but it is now treated as **low-priority / HOLD** rather than required.

Preferred order when you do not want to modify Golden Baseline code:

1. Use an existing external per-problem Golden validation prediction artifact if one already exists.
2. If no prediction artifact exists, run Phase3 in **category-map / CV-design mode** on the deterministic `train.csv`-derived held-out split; accuracy, failure-type counts, and logprob sections remain `NOT_AVAILABLE` until predictions exist.
3. Use available public trajectory artifacts only as auxiliary references, not as the primary Golden CV measurement.
4. Add a logging-only validation runner only later, if measured Golden accuracy/failure/logprob evidence becomes worth the extra operational risk.

If logging is eventually added, the safe logging-only addition should:

- read the same Golden adapter path as read-only;
- use the same prompt, decoding, seed, temperature, max tokens, stop conditions, dtype, and model-loading settings as Golden Baseline;
- run only on a local validation/held-out file with gold answers;
- write `golden_validation_predictions.jsonl` with one row per validation problem;
- optionally write a logprob summary file if the inference backend exposes token scores;
- avoid training/SFT, adapter saving, `adapter_model.safetensors` generation, `adapter_config.json` mutation, `submission.zip` creation, and Kaggle submission.

The logging code should be treated as an observer. It may record the raw output and parsed answer, but it must not alter generation behavior. If an existing external file already contains per-problem Golden validation predictions with gold labels, use that file instead of adding a new logger.

Minimum fields for any future logging-only prediction artifact remain: `problem_id`, `question`, `gold_answer`, `pred_answer`, `raw_output`, `reasoning_text`, `final_answer_text`, `is_correct`, `parse_success`, `parse_error_type`, `generation_token_count`, and `finish_reason`.


## Is Kaggle `train.csv` the validation / held-out file?

`train.csv` is the usual source file to create a local validation/held-out set, because it is the competition-provided labeled data. For Phase3, however, the preferred `--validation` input is **not necessarily the entire `train.csv`**. It should be the exact labeled subset used for Golden Baseline offline evaluation.

Recommended interpretation:

- If you already have a fixed local validation split, use that split file as `--validation`.
- If you do not have a split yet, create a deterministic held-out subset from Kaggle `train.csv` and record the split rule/seed.
- Do not use Kaggle `test.csv` for accuracy/failure analysis because it normally lacks gold answers.
- Do not evaluate on rows that were used to train/tune the Golden adapter if the goal is an honest weakness analysis.

Typical offline Kaggle source path:

```text
/kaggle/input/nvidia-nemotron-model-reasoning-challenge/train.csv
```

A safer Phase3 path would be a derived file such as:

```text
/kaggle/working/phase3_validation_split.csv
```

That derived file should contain at least `problem_id` (or `id`), `question` (or `prompt`/`problem`), and `gold_answer` (or `answer`/`target`/`label`). If the competition `train.csv` uses different column names, map them to these semantic fields before running Phase3.

4. **Do not use `test.csv`** for CV accuracy/failure analysis because gold answers are not available locally.
